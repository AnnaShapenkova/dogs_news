## Сбор и обработка

Collector читает пять засеянных источников: три HN-запроса об AI/Anthropic/OpenAI, arXiv cs.AI и RSS Хабра об ИИ. Берёт до 15 записей из каждого. Сбой чтения одного источника логируется и не останавливает остальные; даже при недоступности всех источников прогон может закончиться finished с нулём материалов. Вставка данных может прервать весь прогон.

Дедупликация — только точное равенство URL. URL не нормализуется, DOI и сходство текста не проверяются. HN обычно даёт пустой story_text, arXiv и RSS обрезаются до 1500 символов. Статья по ссылке, PDF и первоисточники отдельно не загружаются. Входной ответ источника целиком не сохраняется.

Worker раз в 10 секунд загружает все `new` по id, последовательно вызывает одну настраиваемую модель через OpenRouter. В prompt попадает до 2000 символов текста. `MODEL` по умолчанию — строка `anthropic/claude-haiku-5.5`; её фактическая доступность у провайдера не проверялась. Смена модели не предлагалась.

Ответ JSON разбирается, но строгой проверки типов и обязательных полей нет: например, строка в about_ai будет оценена как truthy, отсутствие summary может прервать прогон. Сбой вызова/JSON ставит failed; раз в час и на старте failed возвращаются в new без предела попыток. Поиск новых источников, проверка научного качества, первоисточников и рисков отсутствуют.

## Telegram и интерфейсы

Бот понимает /start и /status, подписывает только личные чаты. Отписки командой нет; при HTTP 403 подписчик удаляется. Long polling и рассылка работают в отдельных потоках; offset хранится только в памяти. При пустом TELEGRAM_TOKEN работает только HTTP-лента.

Раз в 60 секунд бот проверяет незавершённый сбор и очередь new, затем рассылает одну сводку по всем неотправленным находкам, с пятью последними и разбивкой по компаниям. Это приближение к «одна сводка на сбор»: строгой привязки рассылки к run_id нет. При отсутствии подписчиков setup помечает старые находки отправленными. sent_at общий для находки, не для подписчика: HTTP-ошибка доставки отдельному подписчику не мешает поставить его всему пакету; возможны потери и повторы при сбоях.

Mini App обслуживается компонентом bot на `/`; до 300 находок встроены JSON в HTML. Обычный браузер также поддерживается; Telegram SDK добавляет кнопки и навигацию. Поле entity в payload называется reason, но означает компанию, а не обоснование. Есть фильтры по времени и компаниям, карточка и переход к оригиналу. Нет отдельного API ленты и пагинации. `/health` проверяет БД. Публичные GET не требуют авторизации; встраиваются также сведения о модели и общие счётчики, включая число подписчиков, но не их chat_id/имена.

Все findings без редакционного фильтра доступны в Mini App, служебной web-странице, /start и рассылке. Поэтому замены источников и prompt недостаточно для безопасного медиа.

## Развёртывание и зависимости

Python 3.12 задан в `.python-version` и Dockerfile. Единственная сторонняя Python-зависимость — `psycopg[binary]==3.3.6`; HTTP, XML, Telegram, OpenRouter и web используют стандартную библиотеку. `.env` сам код не загружает, переменные должны попасть в окружение извне. В `.env.example` нет всех поддержанных переменных: например, MINI_APP_URL, PORT, TELEGRAM_API. Из Docker BLOCK передаётся аргументом через shell; прямой `python main.py` переменную BLOCK не читает.

Compose содержит PostgreSQL 17-alpine с постоянным pgdata и healthcheck, worker, bot. В нём нет web, collector и встроенного планировщика. Комментарий о задаче внутри worker означает внешнюю настройку Coolify, а не scheduler в Python. README описывает Railway cron раз в шесть часов и отдельную задачу Coolify; фактические настройки облачных аккаунтов не проверялись. PostgreSQL readiness есть, healthcheck приложения в Compose отсутствует.

README для Railway просит порт 8080, а web по умолчанию слушает 8000: нужно явно согласовать PORT. Coolify-зависимые SERVICE_* переменные требуют настройки при обычном локальном Compose. Нет версии миграций, процедуры backup/restore и проверенной инструкции отката.

## Существенные ограничения

1. Полное содержимое первоисточников и доказательства не сохранены; по одному заголовку нельзя выпускать научное объяснение.
2. findings ограничен одной записью на материал; повторная обработка с ON CONFLICT не обновит старый результат. Истории анализов и исправлений нет.
3. Worker не резервирует задачи и не блокирует материал. Несколько worker могут одновременно обработать одну запись и оплатить повторные запросы.
4. Autocommit разделяет вставку finding и изменение status; сбой оставляет частичное состояние. Не все ошибки worker закрывают runs как failed.
5. `CREATE IF NOT EXISTS` и один ALTER — не система управляемых миграций. Засев AI-источников повторяется при каждом init_schema: удалить строки недостаточно, они вернутся; active=false сохранится.
6. Отсутствует граница допуска между генерацией и публичным показом. Низкий риск нельзя вывести из факта наличия summary.
7. Сбор/обработка недоверенного текста не защищены отдельным механизмом от инструкций внутри материала; будущий допуск должен проверять результат независимо от генерации.

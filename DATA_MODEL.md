# Модель данных

Статус: существующая схема подтверждена `db/schema.sql`; будущие сущности описаны концептуально и не утверждены. SQL-миграции не выполнялись.

Уточнение T01: SPEC утверждена; в код добавлен publication_status со значениями draft/published, DEFAULT draft, NOT NULL и CHECK. В таблице ниже отражена исходная схема аудита; новое поле описано в разделе T01. Инициализация на настоящем PostgreSQL пока не проверена из-за ограничения Windows sandbox; статус проверки фиксируется в tests/T01_RESULTS.md.

## Существующая PostgreSQL

| Таблица | Поля и ограничения |
|---|---|
| sources | id SERIAL PK; name TEXT NOT NULL UNIQUE; kind TEXT NOT NULL; url TEXT NOT NULL; active BOOLEAN NOT NULL DEFAULT true |
| runs | id SERIAL PK; service/status TEXT NOT NULL; started_at TIMESTAMPTZ NOT NULL DEFAULT now(); finished_at TIMESTAMPTZ NULL; items INTEGER NOT NULL DEFAULT 0; note TEXT NULL |
| materials | id SERIAL PK; source_id INTEGER NOT NULL FK sources; run_id INTEGER NULL FK runs; url TEXT NOT NULL UNIQUE; title TEXT NOT NULL; text TEXT NULL; published_at TIMESTAMPTZ NULL; collected_at TIMESTAMPTZ NOT NULL DEFAULT now(); status TEXT NOT NULL DEFAULT new |
| findings | id SERIAL PK; material_id INTEGER NOT NULL UNIQUE FK materials; entity TEXT NULL; summary TEXT NOT NULL; model/prompt_version TEXT NOT NULL; created_at TIMESTAMPTZ NOT NULL DEFAULT now(); sent_at TIMESTAMPTZ NULL (добавляется ALTER) |
| subscribers | chat_id BIGINT PK; name TEXT NULL; started_at TIMESTAMPTZ NOT NULL DEFAULT now() |

Связи: sources 1:N materials; runs 1:N materials (необязательная связь); materials 1:0..1 findings. Прогоны worker и bot не связаны с результатами внешними ключами. Индексы, кроме PK и UNIQUE, явно не созданы. Значения kind/status описаны комментариями, но CHECK/ENUM не ограничены. Каскадного удаления нет.

Фактические состояния material: new → done / skipped / failed; failed → new при повторе. findings.sent_at означает общую отметку отправки, а не редакционный допуск и не подтверждение доставки каждому подписчику.

В `props/findings.sqlite` другая демонстрационная модель: sources(id, name) и findings(id, source_id, published_at, company, summary, url). Пять источников и 65 находок. Это не альтернативная рабочая БД приложения.

## Пробелы

Сохранённый material отделён от finding, но text часто пустой или обрезанный. Нет исходного сетевого ответа, снимков документа, DOI, авторов, типа исследования, рецензирования, вида доступа и проверок источников. UNIQUE(material_id) не позволяет сохранять повторные анализы как отдельные версии. Нет тематик, полного текста публикации, решения о допуске, связи отдельных утверждений с доказательствами, истории исправлений и доставки по подписчикам.

## Минимальное дополнение для T01 — предложение

Историческое описание T01 ниже относится к началу проекта. После T01 пользователь сообщил о запуске системы; для последующих изменений уже требуется обновление существующей БД.

Пользователь выбрал вариант A из ARCHITECTURE — расширение findings. Предлагаемый контракт T01: findings.publication_status TEXT NOT NULL с CHECK:

- draft — новые результаты, значение по умолчанию; не показываются;
- published — явный допуск; только они доступны читателю.

Статус обработки material и публикации finding независимы. sent_at сохраняет прежнее значение и не открывает доступ. Переход к published не производится worker в T01. Временно опубликованных записей может не быть. Признак риска и журнал решений потребуются перед включением автопубликации, отдельной задачей.

Пользователь подтвердил отсутствие рабочей БД: итоговая схема создаётся сразу при первом init_schema. Повторная инициализация не меняет статусы уже созданных записей. Отдельная миграция старой production-БД и статус legacy_hidden в T01 не нужны. Имеющиеся в props AI-примеры в PostgreSQL не импортируются. Если позднее появится требование использовать существующую БД старой схемы, для неё потребуется отдельный согласованный план миграции; CREATE IF NOT EXISTS сам по себе её не обновит.

## Предполагаемая модель полноценной редакции

T02 утверждена и подготовлена в коде: materials.raw_payload JSONB NULL и content_scope TEXT с допустимыми abstract/feed_excerpt/metadata_only/legacy_unknown. Новый статус входа — collected, который не забирается нынешним AI-Worker. Новых таблиц нет. Предусмотрено сохранение старых строк и транзакционное идемпотентное обновление; PostgreSQL-проверки пока не выполнены. Исходный снимок не перезаписывается при повторном сборе. Контракт — SPEC.md; результаты — tests/T02_RESULTS.md.

Ниже обязанности данных, а не разрешение создавать все таблицы сразу.

| Сущность | Что хранить и зачем |
|---|---|
| Источник сбора (sources) | Тип, URL, активность; отдельно от научного документа, подтверждающего вывод |
| Исходный материал / снимок | URL, канонический идентификатор/DOI при наличии, дата сбора, доступное содержание, hash, уровень доступа (полный текст/реферат), результат загрузки и условия хранения |
| Попытка анализа | material_id, версия входа/hash, model, prompt/rules version, дата, структурированный результат и ошибка; новые попытки не затирают историю |
| Публикация | Формат, темы, заголовок, текст, краткое описание, размещение (лента/библиотека/оба), статус, актуальная версия, даты публикации и обновления |
| Утверждение и доказательство | Тип утверждения (результат/гипотеза/интерпретация/совет), ссылка на внешний документ и фрагмент/локатор, ограничения, качество доказательств; связь N:M |
| Решение о допуске | Уровень риска, причины, результаты проверок, версия правил, субъект/процесс решения и время; ошибка удерживает публикацию |
| Версия и исправление | Предыдущий и новый текст, причина, дата, автор/процесс, необходимость уведомления; история не перезаписывается |
| Доставка (позже) | publication/version + chat_id + результат/попытка + Telegram message_id, если нужен контролируемый повтор и исправление |

Рекомендация — сохранять исходные данные, анализы и версии публикаций раздельно внутри PostgreSQL; способ хранения полных файлов и допустимые объёмы определить после выбора источников. Повторный анализ использует сохранённый вход без повторного сбора и сохраняет новую попытку. Если сохранён только реферат, повторный анализ не должен представлять его полным текстом.

Демонстрационные AI-записи остаются в props и не импортируются автоматически. Удаление, перенос, переписывание схемы, установка расширений PostgreSQL или векторного хранилища требуют отдельной утверждённой задачи. Персональные профили владельцев/собак сейчас не вводятся; chat_id и имена подписчиков не являются источниками научных данных.

## Локально реализованная T15 — продолжение ступеней

Это дополнение описывает код T15, не подтверждённую приёмку PostgreSQL/Coolify. Новых таблиц и SQL-миграции нет. В materials.editorial_result сохраняются version=2, material_id, input_hash, rules_version, prompt_version, model, attempt_id, stage, phase, stages и next_stage для отложенного продолжения. Каждая запись stages содержит программную ступень, outcome, draft/review при наличии и известный код причины. Сырые материалы остаются в materials.raw_payload отдельно от генерации.

Для сохранения прогресса при откате основной транзакции тот же аудит записывается отдельным autocommit-соединением в runs.note категории worker_attempt. Notes worker_model_call имеют структурированный version=2 с material_id, rules, phase, format_stage и reason; завершение сохраняет metadata. Это категории журнала, не новые процессы. Исторические строковые notes не приводятся к JSON в SQL и не считаются новым одобрением. Неопределённый оплаченный вызов не повторяется автоматически.

Публичный findings.publication_payload получает необязательное stage=1/2/3; метка формата создаётся программой по allowlist. История, причины и тексты рецензий не передаются читательской проекции. Старые payload без stage читаются как прежде. Откат к T14 требует отдельного решения для collected с незавершёнными stages: старый код не умеет их продолжать; данные и бюджет не удалять.

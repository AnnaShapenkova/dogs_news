# T12 — получение примеров на Coolify

Код T12 сначала должен попасть в main после согласованного коммита/push. До обновления команды нового модуля на стенде не существуют. Пользователь выполняет развёртывание сам; резервную копию существующей БД сохранить, том не пересоздавать. Схема БД не меняется.

## После обновления

Новые collected обрабатываются Worker автоматически в пределах бюджета. В /status видны публикации, попытки и модельные вызовы за сутки UTC, точные причины и время следующего окна. Рассылка принимает только published.

Если очередь есть и бюджет не исчерпан, сначала дождаться обработки collected и посмотреть /status. Повтор старых held/error необязателен и выполняется только явно. Старые находки в published вручную не переводить.

## Выбор материалов — только чтение

В Terminal сервиса worker, из корня приложения:

```sh
python -c "import db; c=db.connect(); rows=c.execute(\"SELECT id,title,status,editorial_result->>'reason' FROM materials WHERE status IN ('held','error') ORDER BY id LIMIT 30\").fetchall(); print(*rows,sep='\n'); c.close()"
```

Команда не показывает ключи и не меняет строки. Выбрать до 15 ID. Например, вместо 101 и 102 подставить реальные номера:

```sh
python -m worker.requeue --ids 101 102
```

Это предпросмотр: `eligible: true` означает пригодность для повторной проверки, не одобрение публикации. Если список подходит и повтор согласован, явная запись:

```sh
python -m worker.requeue --ids 101 102 --apply
```

Если хотя бы один выбранный ID непригоден, вся пачка остаётся без изменений. `requeued: true` подтверждает постановку; прежнее решение сохранено в runs. Повтор этой версии для одного материала невозможен. Публикации, сомнительный статус и дубли не возвращаются. Команда не вызывает модель и Telegram сама, но работающий Worker может сразу начать обработку collected, потратить бюджет и опубликовать/разослать результат. Применять только к выбранному согласованному списку.

## Что прислать для анализа

Обновлённый /status, текст хотя бы одной публикации с источником и ограничениями, подтверждение получения сообщения. Если снова 0 — точные новые причины (например, ответ усечён / неверный JSON / проверка текста не пройдена), без API-ключей. Это основание для следующего исправления, а не повод отключать проверки.

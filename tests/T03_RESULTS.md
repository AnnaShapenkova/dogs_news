# T03: состояние перед фиксацией для стенда

Код подготовлен по утверждённой T03. По просьбе пользователя дальнейшие проверки остановлены; следующие проверки он выполняет на стенде. Коммит и push из среды агента заблокированы правами записи .git; подготовлен локальный файл фиксации и отправки в main. На сервере агент ничего не разворачивал и реальные платные вызовы/публикации не запускал.

## Фактически выполнено

- Последний запуск: **72 Python-теста, 41 пройден, 31 пропущен** из-за отсутствия тестовой PostgreSQL. Это не подтверждает прохождение SQL/конкурентных/HTTP-интеграционных сценариев.
- Node: пустое состояние, карточка опубликованной статьи, темы, ссылки/ограничения и экранирование — пройдены.
- Подготовлены 12 синтетических контрольных случаев: 3 допустимых варианта текста, 3 с недостаточными доказательствами, 4 с риском, 2 с недоверенными инструкциями/ошибкой источника. Это проверка механизма, не оценка научной истинности реальных исследований.
- Реальные ответы модели для этих публикаций не получались, деньги OpenRouter не расходовались агентом. Пример drafts/publication-preview-01.md остаётся отдельным неподтверждённым редакторским черновиком.

## Реализация

worker/editorial.py проверяет идентификаторы и доступную аннотацию Europe PMC, научный статус, явную связь популярной статьи с DOI/MED:id, строгие контракты, подтверждающие фрагменты, числа и консервативные ограничения риска. Один материал может быть опубликован только после генерации и отдельного reviewer-запроса той же модели. Корреляция ошибок этих запросов остаётся ограничением.

worker/main.py выбирает collected, резервирует попытки/вызовы в runs через отдельное autocommit-соединение, атомарно сохраняет published и done либо held/error с аудитом. Резервирование сериализуется транзакционной блокировкой, обработчики — существующим механизмом advisory lock и блокировкой кандидата. Начавшийся вызов расходует лимит даже при падении процесса. Дневные лимиты и конкурентные сценарии требуют проверки на PostgreSQL.

В findings добавлены publication_payload и published_at, в materials — editorial_result. Уникальный индекс научной основы предотвращает две первоначальные публикации об одной работе. Исходный raw_payload не переписывается. Новых таблиц/сервисов/моделей нет.

publication.py экспортирует только публичные поля. Mini App и web показывают текст, ограничения, источник и дату публикации; техническая трассировка из карточки убрана. Telegram сохраняет текущий механизм отправки опубликованных записей; backlog collected/held/старых AI-new не блокирует отправку. /status показывает агрегированные причины. Общая sent_at не является индивидуальным подтверждением доставки каждому подписчику; существующее ограничение доставки при падении/ошибке не объявляется исправленным.

## Перед самостоятельным тестом на стенде

Остановить Worker и рассылку, сделать backup существующей БД/тома. Схема обновляется идемпотентно в init_schema при запуске; данные/том не удалять. Сначала запуск без ключа модели оставляет collected и не делает платных вызовов. При включении ключа Worker начинает реальную обработку; Telegram-токен включает реальные отправки. Для пробного запуска можно оставить TELEGRAM_TOKEN пустым: Mini App работает, сообщения не отправляются.

Collector сам по расписанию не запускается; однократная команда — python main.py collector. Если все кандидаты удержаны, смотреть /status и логи Worker; published вручную всем записям не выставлять. Старый Worker/образ не возвращать на новый корпус без остановки обработки. Полная PostgreSQL-проверка остаётся отдельным невыполненным шагом.

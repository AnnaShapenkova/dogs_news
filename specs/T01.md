# T01 — отделить черновики от опубликованных находок

Статус: УТВЕРЖДЕНО пользователем сообщением «утверждаю». Код T01 подготовлен; полная приёмка ожидает PostgreSQL-проверок. Пользователь разрешил коммит и push с незавершённой проверкой и проведёт оставшиеся тесты в Coolify. Отчёт: [tests/T01_RESULTS.md](../tests/T01_RESULTS.md).

Дата: 2026-11-12. База аудита: `6b5ecc35fc80c8dcac6a490818f089c53a28dd42`.

Уточнение пользователя: действующей версии и БД нет; целевая платформа — Coolify. Первая задача рассчитана на новую пустую PostgreSQL, без переноса прежних данных и без развёртывания.

## Проблема и текущее поведение

Worker создаёт findings для AI-материалов; каждая находка сразу видна в Mini App, web, /start и очереди рассылки. `materials.status` описывает обработку, `findings.sent_at` — отправку; ни одно поле не обозначает редакционный допуск. Замена prompt и источников сейчас открыла бы читателю непроверенный AI-текст.

## Цель одной задачи

Ввести техническую границу публикации: новый результат остаётся скрытым черновиком, читатель получает только явно опубликованные записи. Новая БД сразу создаётся с этим контрактом. Демонстрационные записи props не импортируются. T01 не реализует классификатор риска и не включает автопубликацию. Целевой режим пользователя — автопубликация низкорискового проверенного контента — будет реализован отдельным этапом допуска после проверок источников и доказательств.

## Рассмотренные варианты и выбранное решение

A: добавить статус в findings. Плюсы: небольшой объём и сохранение существующих связей; минусы: ограничения одной записи на материал сохраняются.

B: ввести отдельную publications сразу. Плюсы: чётко отделяет редакционный текст и подходит будущей библиотеке; минусы: больше схемных изменений и новый путь данных.

Пользователь выбрал A: расширяем findings. Отдельную publications в T01 не создаём. SPEC утверждена для реализации одной задачи T01.

## Контракт выбранного варианта A

Добавить findings.publication_status: NOT NULL, DEFAULT draft, CHECK на draft / published. Статусы обработки material не менять. Значение published может в дальнейшем выставлять только согласованный механизм допуска, которого в T01 ещё нет.

На пустой БД init_schema создаёт итоговую схему с default draft. Повторный запуск init_schema не сбрасывает статусы и содержимое записей. Существующий advisory lock при инициализации сохраняется. sent_at не используется как признак допуска.

Миграция прежней production-БД, статус legacy_hidden, журнал миграций и миграционный фреймворк в T01 не входят: переносить данные неоткуда. Старая схема существующей БД не является поддержанным сценарием этой задачи; если такое окружение появится, потребуется отдельный план. Для тестирования использовать только изолированную БД, создаваемую с нуля.

## Изменения по компонентам

| Компонент | Изменение |
|---|---|
| db/schema.sql | Статус и ограничение при создании новой БД; повторная инициализация сохраняет данные |
| worker | Явно или через DB default создаёт только draft; не может автоматически поставить published |
| bot.page_data | Только published в findings, читательских счётчиках findings и показателях kept/sent |
| bot.handle (/start) | Приветственные последние записи — только published |
| bot.send_new / setup | Сводка и sent_at работают только с published; черновики не помечаются отправленными |
| bot.status_text | Счётчик читательских находок только published; оперативные сведения о runs сохраняются |
| web.render | Счётчик и список находок только published |
| template.html | Проверить пустую ленту; заменить обещание появления сразу после разбора на ожидание публикации |
| collector / main.py / Dockerfile / зависимости | Функциональных изменений нет |

Служебные счётчики materials/runs могут сохранять общее количество входов; они не должны раскрывать текст черновика или представлять его опубликованной находкой. В этой задаче не создаётся редакторский интерфейс. Для проверки published допускается только подготовка фикстуры в изолированной тестовой БД, без команды публикации в production.

## Не входит

Замена AI-источников и prompt, новые темы/форматы, автоматическое решение о риске, проверка первоисточников, новые модели и сервисы, библиотека, помощник, новая система доставки, исправления публикаций, выбор хостинга, развёртывание. Не исправлять прочие проблемы аудита попутно.

## Проверяемые критерии приёмки

1. Первый init_schema на пустой БД создаёт итоговую схему. После добавления тестовых draft/published повторный init_schema сохраняет строки, связи, статусы и sent_at. Данные props не импортируются.
2. INSERT без статуса создаёт draft; NULL/неизвестное значение отклоняются PostgreSQL.
3. В смешанной фикстуре (draft, published, отправленные и неотправленные) ни один читательский путь не возвращает текст/ссылку скрытой находки. Счётчики опубликованных находок совпадают с выдачей.
4. /start и сводка содержат только published. Наличие одного draft не добавляет его в сообщение. Ни send_new, ни setup не меняют sent_at у скрытых записей.
5. Результат worker по замоканному ответу модели остаётся draft и не виден читателю. Непроверенные данные никогда не получают published автоматически.
6. При отсутствии published Mini App и web отображают корректное пустое состояние; /start не выдаёт скрытые последние записи. Сводка без опубликованных неотправленных находок не отправляется.
7. После явного добавления published фикстуры она видна в обоих HTTP-интерфейсах, /start и сводке; прежняя логика ограничения LATEST сохраняется.
8. Тесты не обращаются к настоящим Telegram/OpenRouter и не используют производственную БД. Не добавлены новые сторонние зависимости, сервисы и модели.

## План проверки

Написать изолированные тесты стандартным unittest с подменой Telegram и модели для формирования выдачи и сообщений. Отдельно интеграционные тесты PostgreSQL на одноразовой БД для первого и повторного init_schema, DEFAULT/CHECK и реальных SELECT, потому что макеты SQL не доказывают корректность фильтрации. Подготовить фикстуру смешанных статусов. Проверить пустое состояние HTTP и Mini App. Выполнить таблицу «критерий → тест → результат» и git diff --check.

На этапе аудита интеграционная среда отсутствовала. Для T01 внутри игнорируемой .tools подготовлены Python 3.12.10, существующая зависимость psycopg 3.3.6 и переносимые файлы PostgreSQL 17.6. initdb не смог создать кластер из-за ошибки Windows sandbox при создании restricted token. Поэтому PostgreSQL-тесты пока пропущены; отсутствие работающей БД не считается успешной проверкой. Способ продолжения приёмки предложен пользователю; команды локального запуска вне sandbox приведены в tests/README.md.

## Риски и откат

Лента новой БД сначала пустая, а текущая AI-обработка при тестировании будет накапливать скрытые черновики. Это ожидаемое промежуточное состояние до тематической обработки и механизма допуска. Действующих читателей и данных T01 не затрагивает. Сбор и отправки реальным пользователям в этой задаче не запускаются.

Откат при разработке выполняется только в изолированном тестовом окружении. Автоматическое удаление данных и томов не допускается. Возврат старого кода при новых данных снова покажет все findings: такой откат не считается безопасным. До будущего развёртывания в Coolify отдельная задача должна описать резервное копирование, восстановление и совместимость отката кода со схемой.

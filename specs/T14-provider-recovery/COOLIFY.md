# T14 — обновление и возобновление на Coolify

Код сначала должен попасть в main отдельным согласованным коммитом. Агент не выполнял отправку или развёртывание. Сохранить резервную копию рабочей БД; том не пересоздавать. Новых SQL-миграций нет.

## Ключ и средства

Новый OPENROUTER_API_KEY задаётся в Environment Variables Coolify, без публикации в Git/чатах. Убедиться, что ключ имеет доступ к положительному балансу и достаточному лимиту; новый ключ того же аккаунта не пополняет баланс. Применить переменную при обновлении/пересоздании контейнера средствами Coolify. Ключ не выводить в терминал.

## Версия Worker

После обновления в Terminal именно контейнера worker:

```sh
python -c "from worker.editorial import RULES_VERSION; from worker.main import PROMPT_VERSION, OUTPUT_TOKENS; print(RULES_VERSION, PROMPT_VERSION, OUTPUT_TOKENS)"
```

Ожидается `dogs-pilot-v4 dogs-v4 {'draft': 6000, 'review': 2400}`. Команда только читает код.

## Состояние и явное возобновление

```sh
python -m worker.provider
```

Предпросмотр читает состояние БД, не вызывает OpenRouter, ничего не меняет и не подтверждает доступный баланс. Если paused=false, снимать паузу не требуется. Если paused=true, после проверки средств явное возобновление:

```sh
python -m worker.provider --resume
```

Эта команда запишет событие возобновления, не очистит бюджеты и не изменит материалы. Работающий Worker может сразу начать платные запросы, публикацию и рассылку для имеющихся collected. При повторном 402 после одной попытки снова включится пауза. Смена ключа, перезапуск и новые сутки сами её не снимают.

Если журнал повреждён, команда откажет: не удалять историю, показать текст ошибки для отдельного разбора. При обычной оплатной паузе /status объясняет её и безопасную причину (если провайдер её передал). Отсутствие limit_source не доказывает конкретную причину 402.

## Очередь и дневной бюджет

Отправить боту `/status`. При исчерпанных 15 попытках ждать 00:00 UTC / 03:00 Москвы, даже после снятия паузы. Не менять timestamps и не удалять runs. Максимум 3 публикации и 30 модельных вызовов также сохраняется.

Старые ошибочные материалы не вернутся сами. После согласования выбранных ID, например ID 405 и 413 из диагностики пользователя, сначала предпросмотр:

```sh
python -m worker.requeue --ids 405 413
```

Подставлять только реальные выбранные ID. Если eligible=true и повтор этих материалов согласован:

```sh
python -m worker.requeue --ids 405 413 --apply
```

Если хотя бы один ID непригоден, вся пачка не меняется. Предыдущее решение сохраняется в runs; один повтор на текущую версию правил. Не возвращать всю очередь и не присваивать published вручную. Если есть collected и доступный бюджет, новый сбор не нужен.

## Результат для анализа и откат

Прислать /status и хотя бы одну полученную публикацию с источником и ограничениями. При 0 публикаций — новые точные причины; не считать задачу принятой только по успешному деплою.

Для PostgreSQL-тестов использовать отдельную изолированную БД по tests/README.md, не рабочую DATABASE_URL. Откат: остановить Worker, сохранить аудит и вернуть T13. Поскольку T13 не учитывает паузу оплаты, не запускать его до устранения 402; данные/журнал не удалять.
